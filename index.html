venue-integrationin productionLuna Rooftop and The Lobby117 offline tests

Match every booking to what the table actually spent

Reservations-to-POS reconciliation across two different POS systems. A deterministic scoring engine matches each reservation to its check and records why, then reports minimums, no-shows, revenue by section, and deposits.

TypeScriptNode 22SQLiteToast APITableList API
View the code
The problem

The booking system and the POS share no common identifier. A party moves tables, one order carries two checks, and a 1:30am check belongs to the previous business date.

What changed

A scored matcher pairs reservations to checks and records the reason for every match, so a disputed number can be traced back to the evidence rather than argued about.

▸How it was builtLuna Rooftop and The Lobby Social Bar, nightly
  1. Wrote one PosAdapter interface with two implementations, so a venue picks its POS in config rather than forking the codebase.
  2. Built a business date rule into the domain model: the night runs 6pm to 6am, so a 1:30am check belongs to the prior calendar day. Getting this wrong silently splits a night in half.
  3. The matcher scores each candidate on table, time window, party size, and whether the deposit shows up as a tender line, then assigns greedily so one check can never satisfy two reservations.
  4. Every match stores its reasons, and the leftovers surface as no-show, walk-in, or possible split rather than being dropped.

Built for the two venues I co-own because the reports we needed did not exist in either vendor's product. It runs against the real APIs and against recorded fixtures, so the whole pipeline runs offline with no credentials.

Walks orders to checks to selections and groups by table, because the sales screen only renders the check layer. Every money identity verified against the live API, not taken from the docs.

PythonToast APIReconciliation

The problem

The POS model puts money on the check and the table on the order one level up, so the table never appears on the sales screen at all.

What changed

Groups by table across orders, excludes voided and denied payments, and reconciles the money identities so the totals can be trusted against the vendor's own reports.

▸How it was builtPublic version of a nightly tool, synthetic data
  1. Verified against a real night that check.amount is item sales plus the card surcharge, so the number the vendor UI labels subtotal is not pure product sales.
  2. Found the double-count trap: one check carried a voided payment and a captured payment for the same amount, so naive summing inflates revenue.
  3. Made the spend basis configurable across four definitions, because the answer to "what did they spend" legitimately differs depending on who is asking.
  4. Wrote a reconciliation command that proves the pull is complete and the money identities hold, since the API exposes no sales summary to diff against.

The private version runs against a real venue account. This public repo is the same code against a synthetic fixture that reproduces every edge case that bit the original: table moves, split checks, voided payments, and an open check.
